# Integration contract: agent → engine → manager → console / response

Status: **capstone contract, v1 (2026-10-25).** This document records the data
shapes the components already exchange, plus the additive fields introduced for
the capstone. Where a shape is owned elsewhere, this file points at the owner
instead of redefining it.

```
Officer agent ──NDJSON 0.2–0.4──▶ manager POST /api/v1/ingest ──events table (detect_state)──▶
  detection worker ──OfficerIngestionAdapter──▶ DetectionRun.process_event ──Alert──▶ AlertSink
     ├─ alerts            (every Alert, INSERT OR IGNORE on alert_id)
     ├─ incidents         (Alert.incident_id set → upsert; revision only moves forward)
     ├─ incident_alerts   (incident ↔ member alerts, from evidence.stages[].alert_id)
     └─ response_actions  (Alert.active_response → response_engine.translate_recommendation
                           → policy → PENDING / auto-authorized / REJECTED)
  console ──server-side proxy, analyst bearer──▶ manager GET /api/v1/{alerts,incidents,response-actions,status}
  analyst ──console──▶ POST /api/v1/response-actions/{id}/{authorize|reject} ──▶ commands ──▶ agent poll
```

## 1. Agent → ingestion

Owner: `panopticon-agent/schema/event.schema.json` (0.2–0.4) and
`panopticon-manager/manager/wire/telemetry.py` (`TelemetryEvent`, `extra="forbid"`).
The engine's `ingestion/officer_adapter.py` turns one wire event into the flat
canonical event below. Malformed events are rejected per event at ingest (the
batch still returns 200 with per-event `rejected[]`); duplicates collapse on
`event.id` (`INSERT OR IGNORE`).

## 2. Ingestion → detection (canonical event)

`officer_adapter.transform_officer_event(raw) -> dict`, consumed by
`DetectionRun.process_event(event) -> list[Alert]`. Key fields: `event_id`,
`event_type` (`process_create`, `network_connect`, `file_create`, `file_delete`,
`registry_write`, `image_load`, and the 0.5 families), `timestamp` (ISO-8601 UTC),
`host_id`, `process{pid, name, executable, command_line, entity_id,
start_time_ticks, parent{pid, name}}`, plus one family block. The full field
list is `ingestion/telemetry.FIELD_REGISTRY` (generated by running the
normalizer).

## 3. Detection → everything downstream (the Alert)

`panopticon_detection.alerting.alert.Alert.to_dict()`:

| Field | Type | Meaning |
|---|---|---|
| `alert_id` | str | Deterministic. Rule alerts `ALT-<sha1>` of (rule, event, host, ts, evidence keys); incident revisions `INC-…-R<n>`; host risk `RISK-…`; beacons `ALT-BCN-…`. Replaying an event yields the same id. |
| `rule_id` | str | YAML rule id, `PROV-CAMPAIGN` (incident), `CORR-RISK-001` (host risk), behavioural detector id. |
| `detection_source` | str | **New.** `rule` \| `stateful` \| `behavioral` \| `correlation`. |
| `title`, `description` | str | From the rule, or derived from the incident. |
| `level` | int 0–16 | Wazuh-style. |
| `severity` | str | `low` \| `medium` \| `high` \| `critical`. |
| `confidence` | float 0–1 | **Analyst-assigned prior from the rule YAML, not a calibrated probability.** Incidents take the minimum over their technique stages. Never used alone to authorize a response. |
| `host_id`, `timestamp`, `event_id` | str | Of the triggering event (`timestamp` is event time). |
| `evidence` | object | Matched fields (`process.name`, `process.command_line`, …), `matched_conditions`, enrichment context. Incident alerts: see §4. |
| `active_response` | object \| null | A *recommendation*: `{action, host_id, target_pid, target_guid, target_start_time_ticks, target_file, reason}`. Vocabulary: `TERMINATE_PROCESS`, `COLLECT_PROCESS_INFO`, `COLLECT_NETWORK_CONNECTIONS`, `QUARANTINE_FILE`, `ISOLATE_HOST`. |
| `mitre_tactic`, `mitre_technique` | str \| null | ATT&CK mapping. |
| `incident_id` | str \| null | Set only on incident alerts; stable across revisions. |
| `tags`, `compliance` | list[str] | |

### Alert, incident, campaign: definitions

- **Alert** — one detection: a rule match, a stateful-rule completion, a
  behavioural signal, or a correlation result. Repeats of the same rule on the
  same process within 10 min are suppressed (`DetectionRun.dedup_ttl_seconds`).
- **Incident** — a set of detections whose processes are causally connected in
  the provenance graph (backward along information flow + forward from the tree
  entry point, both stopping at boundary processes such as `explorer.exe`). It
  opens only when a terminal-tactic detection at level ≥ 10 has ≥ 2 stages over
  ≥ 2 tactics in its scope. Same host alone never merges two incidents.
- **Campaign** — used as a synonym for a multi-stage incident (`rule_id:
  PROV-CAMPAIGN` is a stored name kept for compatibility). Cross-host campaigns
  are out of scope.

## 4. Incident alert evidence (PROV-CAMPAIGN)

`evidence` on an incident alert carries: `incident_id`, `revision`,
`attack_chain`, `stage_count`, `stages[]` (`time, rule_id, rule_name, tactic,
technique, process, pid, event_id, alert_id`), `tactics_covered`,
`root_cause_process`, `root_pid`, `root_inferred`, `process_lineage`,
`provenance_origin`, `processes_in_scope`, `causal_path[]`, `incident_score`,
`score_breakdown`, `why[]`, `updates_since_last_alert`.

A new revision is emitted only when the incident gains a tactic or its severity
band rises. `stages[].alert_id` is **new**; it is `null` for a stage whose
detection was suppressed as a repeat.

## 5. Detection → persistence (manager)

| Table | Key | Written when |
|---|---|---|
| `alerts` | `alert_id` PK | every emitted alert (`INSERT OR IGNORE`) |
| `incidents` | `incident_id` PK | an alert with `incident_id`; upsert, `revision` only increases; analyst `status` is never overwritten by the engine |
| `incident_alerts` | (`incident_id`, `alert_id`) PK | each revision alert and each `stages[].alert_id` |
| `incident_audit` | `audit_id` PK | incident opened / revised / analyst status change |
| `response_actions` | `response_id` PK | new alert with `active_response` |
| `commands`, `command_results`, `command_audit` | existing | authorization → dispatch → result |

Transaction boundary: one event = one `BEGIN IMMEDIATE` covering its alerts,
incident upserts, response staging and `events.detect_state='done'`.

## 6. Detection → response (policy)

Owned by `panopticon-response-engine` (tiers, translation) and
`panopticon-manager/manager/detection/response.py` (staging). The capstone policy:

| Class | Condition | Outcome |
|---|---|---|
| 1. Auto | action tier `AUTO_SAFE` (`COLLECT_PROCESS_INFO`, `COLLECT_NETWORK_CONNECTIONS`) — read-only, reversible | authorized as `system:response-engine`, dispatched, audited |
| 2. Approval | `KILL_PROCESS`, `QUARANTINE_FILE`, `ISOLATE_HOST`, … from a `rule`, `stateful` or `correlation` alert | `PENDING` until an analyst authorizes or rejects; expires after 15 min |
| 3. Record only | no recommendation, untranslatable recommendation, missing `start_time_ticks`, or a disruptive action from a `behavioral` alert | `REJECTED` with the reason; alert still shown |

Idempotency: one response action per new alert (gated on the alert insert);
a non-terminal response action with the same (`host`, `action`, target) is not
duplicated by a later alert or incident revision; command ids are
`resp-<response_id>` (duplicate → 409); duplicate results are audited and ignored.
No ML score authorizes anything: there is no ML score on the alert path today.

## 7. Backend → frontend (manager API, analyst bearer)

| Route | Returns |
|---|---|
| `GET /api/v1/alerts?host_id&severity&rule_id&source&incident_id&limit&before` | `{alerts:[{alert_id, rule_id, level, severity, host_id, agent_id, event_id, alert_timestamp, created_at, mitre_tactic, mitre_technique, detection_source, incident_id, alert:{…Alert}}], next_before}` |
| `GET /api/v1/alerts/{alert_id}` | `{alert:{…row}, response_actions:[…]}` |
| `GET /api/v1/incidents?status&host_id&limit` | `{incidents:[{incident_id, host_id, status, severity, level, score, confidence, tactics, stage_count, root_process, revision, first_seen, last_seen, alert_count}]}` |
| `GET /api/v1/incidents/{incident_id}` | `{incident:{…summary, evidence:{…latest incident alert evidence}}, alerts:[…], response_actions:[…], audit:[…]}` |
| `POST /api/v1/incidents/{incident_id}/status` `{status, note}` | status ∈ `open`, `investigating`, `resolved`, `false_positive`; audited with the analyst id |
| `GET /api/v1/response-actions?state` | existing, plus `audit` per action (command_audit rows) |
| `POST /api/v1/response-actions/{id}/authorize` / `reject` | existing |
| `GET /api/v1/status` | `{events:{pending, claimed, done, failed}, alerts, incidents_open, response_actions:{…by state}, agents_enrolled, last_event_at}` |
